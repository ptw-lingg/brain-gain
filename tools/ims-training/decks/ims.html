Jira Issue Management System (IMS)

How defects and improvements are reported, validated, assessed, approved, implemented and closed in the Jira project “Issue Management”.

PTW-Freiburg GmbH · based on AA Jira Issue Management System rev. 001/06.2026 (roXtra 181298) · about 25 minutes

What the IMS is

Overview

The IMS is the validated Jira project in which every defect and improvement of our hardware and software products is recorded and dispositioned. It replaces the Mantis defect management system.

  • Everyone can report. All employees get reporter-level access in Jira.
  • Two work types. Defect — a problem; Improvement — a better property of an existing product.
  • Defined path. Each issue runs through fixed states; every transition is done by a defined role.
  • Compliant record. Risk evaluation, traceability and documentation from report to closure, in line with ISO 13485, ISO 14971 and IEC 62304.
Post-market issues (e.g. customer feedback) follow SOP-21.09 Rückmeldungen. Link the triggering Q-Request in the issue.

Reporting an issue

For everyone: creating a defect or an improvement that can be assessed without follow-up questions.

Creating an issue

Part 1 · Reporting
  • 1
    Open the Issue Management board in Jira and click the red Create button.
  • 2
    Choose the Work type: Defect or Improvement.
  • 3
    Fill in the mandatory Summary (what happens, where) and Product (the affected product).
  • 4
    Set the Assignee to the product’s Project Lead. Not known? Assign the Director Research & Development.
  • 5
    Click Create — the issue starts in state New and the assignee is notified.

What makes a good issue

Part 1 · Reporting

The Project Lead checks every new issue against four criteria. Give as much information as possible up front, so it is not sent back to you.

CriterionValid when …
Descriptionclear and complete
Reproducibilitysteps to reproduce are provided
Expected vs. actualboth behaviours are clearly defined
Evidencescreenshots, logs etc. demonstrate the issue

Use the templates

Description, Reproducibility, System Environment and Context Assessment come with a template that tells you what to enter.

Add references

  • Q-Request, if the issue comes from feedback
  • ID or link from the project’s daily tool, if any
  • Mantis ID for issues carried over from Mantis

Defect or improvement?

Part 2 · Workflow

Defect

Something does not work as specified or intended.

  • Full path incl. Risk Assessment by the QM
  • Safety and Security Risk Assessment fields are shown
  • Severity: Critical · Major · Minor

Improvement

An existing product should get better.

  • Same path, but no Risk Assessment
  • PM moves it from Context Assessment straight to Backlog
  • Risk assessment fields are hidden
Chose the wrong type? During Validate Issue the Project Lead can still switch between Defect and Improvement.

Further fields

  • Medical Device (Yes/No)
  • Change Request · Quality Request
  • AE Link (Aligned Elements)
  • Mantis ID

Assessments by role

What the Project Lead, the Product Manager and the Quality Manager check and decide.

Project Lead: Validity Check

Part 3 · Roles

When you start on a new issue, first move it to Validity Check — so everyone sees it is being looked at. Then check it against the four criteria (description, reproducibility, expected vs. actual, evidence).

OutcomeTransitionResult
ValidRequest Context AssessmentContext Assessment, assigned to the PM
Not enough informationImprove IssueNew, assigned to the Reporter
Invalid / obsoleteReject Issue, Resolution “Invalid”Closed
Selecting the Resolution Invalid triggers an automation: the ticket is unassigned and closed.

Product Manager: Context Assessment

Part 3 · Roles

The PM decides how the issue fits the product and its use, and records the result in the Context Assessment field.

  • Assess: impact on a released product, on usability and on operation; affected versions; reproducibility; frequency; affected users or systems; all attached evidence.
  • Record: all required fields, a summary of the key observations, the Priority, and the Q-Request ID if a released product is affected.

Quality Manager: Risk Assessment

Part 3 · Roles

Defects only. The QM evaluates the risk with regard to the product characteristics and its intended use.

  • Evaluate: impact on safety and security; impact on RAT and SRAT; new or additional risks; technical and application-related risks.
  • Required for approval: overall risk level calculated; acceptance criteria and planned mitigation documented; residual risk clearly stated; all evidence and reference links attached.
OutcomeNext state
AcceptableApprove Issue → Backlog, assigned back to the PL
Details missingImprove Issue → New, Reporter
Sending back? The comment must contain an actionable, bulleted checklist of what is missing — tag the PL or PM if needed.

Implementation and closure

Part 3 · Roles

Backlog

No open questions — ready for the engineering team.

In Progress

PL moves the issue once engineering starts. Implementation needs a Change Request per SOP-10.12 — enter its number in the Change Request field (and the Q-Request number, if any).

Closed

PL closes after confirming: verification complete · all acceptance criteria met · evidence linked.

Reopen

New information about a closed issue? The PL reopens it — it goes back to Context Assessment.

Decided not to fix?

Write the rationale into the description or a comment.

Comments, records and traceability

Part 3 · Roles
  • Comment every transition. Explain the decision in the Comments field; mention people with @name — they are notified.
  • Keep it in the issue. All risk-relevant information belongs into the Jira issue: fields, attachments, comments.
  • Link the controlled documents: FMEA, RAT, SRAT, usability documentation, Q-Request, Change Request.
  • At closure: link the item in the development tool that documents the fix, the test evidence and the key decisions.

Key points

Summary
  • 1
    Every employee can and should report defects and improvements in the IMS.
  • 2
    Work type, Summary and Product are mandatory; assign the Project Lead (fallback: Director R&D) and add evidence.
  • 3
    Path: New → Validity Check (PL) → Context Assessment (PM) → Risk Assessment (QM, defects only) → Backlog → In Progress → Closed.
  • 4
    Improve Issue sends it back to the Reporter; Reject Issue closes it as Invalid.
  • 5
    No implementation without a Change Request; closure needs verification, met acceptance criteria and linked evidence.
